#+title: bevy_shine 光线追踪原型实施计划（GPU LBVH）
#+startup: content
#+author: Gaeric
#+OPTIONS: ^:{}

本文档描述 =bevy_shine= 光线追踪原型的实施计划。

*原则（按优先级）*：
1. **渲染管线完全独立**：沿用 =ShineRenderGraph= 这条自定义 camera schedule，不接入 =Core3d=。
2. **在独立的前提下尽量复用**：只把 Bevy 现成的 *system* 注册进我们自己的 schedule，不接管它的 schedule 所有权。

* 0. 目标与位置
  - 学习/开发工程：=bevy_unit/bevy_shine=（workspace 成员，Bevy 0.19，本地 patch 到 =../bevy_engines/bevy_0.19/=）。
  - 参考工程：=../bevy-hikari=（Bevy 0.13 时代；CPU 建 BVH + compute shader 2 次弹射的 ReSTIR 风格 GI）。
  - 与 hikari 的两点核心差异：
    1. **复用 Bevy 的 prepass / post-processing**，不再自己画 position / normal / instance_material / velocity G-Buffer。
    2. **BVH 改为标准 GPU LBVH 路线**：
       =Morton Code= → =GPU Radix Sort= → =Karras LBVH Topology= → =Atomic Bottom-Up AABB Refit=，
       全部 compute shader 在 GPU 上构建，替换 hikari 的 =bvh= crate（CPU =BVH::build= + =flatten_custom=）。
  - 现状（M0 前的基线，供对照）：=bevy_shine= 只有「自定义 camera schedule + 自定义 binned phase item
    画全屏三角形」的骨架；=light.rs= / =prepass.rs= / =overlay.rs= 是占位。
    **这些已在 M0 期间全部删除**，当前结构见第 3 节。
  - 注释使用英文，且使用小写开头，倾向于随意自由的风格

* 1. 关键前提：自定义 schedule 到底能复用 Bevy 的什么（已逐条核实）
  这是整个方案的可行性基础，必须先钉死。

** 1.1 Bevy 0.19 的 prepass 由哪些部分组成，分别注册在哪里
   | 阶段                                            | 系统                                                | 注册位置                          | 是否依赖 render graph |
   |-------------------------------------------------+-----------------------------------------------------+-----------------------------------+-----------------------|
   | 相机是否要 prepass / 准备 phase                  | =extract_camera_prepass_phase=                       | =ExtractSchedule=（全局）          | 否（只查 =Camera3d= + 组件） |
   | 创建 =ViewDepthTexture=                          | =prepare_core_3d_depth_textures=                     | =Render/RenderSystems::PrepareResources= | 否 |
   | 创建 =ViewPrepassTextures=（depth/normal/motion）| =prepare_prepass_textures=                           | =Render/RenderSystems::PrepareResources= | 否 |
   | prepass mesh 排队                                | =queue_prepass_material_meshes=                      | =Render/RenderSystems::QueueMeshes=  | 否 |
   | prepass 管线特化                                 | =specialize_prepass_material_meshes=                 | =Render/RenderSystems::PrepareMeshes= | 否 |
   | prepass batching / 排序 / buffer                 | =BinnedRenderPhasePlugin::<Opaque3dPrepass, MeshPipeline>= 等 | =Render/...=                | 否 |
   | **真正画 prepass**                               | =early_prepass= / =late_prepass=                      | **=Core3d= schedule**（=Core3dSystems::Prepass=） | 是 |
   | tonemapping                                      | =tonemapping=                                        | **=Core3d=**（=Core3dSystems::PostProcess=） | 是 |
   | upscaling（main texture → out_texture + present）| =upscaling=                                          | **=Core3d=**                       | 是 |

   **结论**：prepass 的「准备/排队/特化/纹理创建/batching」**全部在全局 schedule**，只要相机上有 =DepthPrepass= /
   =NormalPrepass= / =MotionVectorPrepass= 组件就会自动跑，与相机用哪个 =CameraRenderGraph= 无关。
   **只有「画 prepass」这一条在 =Core3d= 里。**

   而这些函数都是 pub 的，可以直接注册到我们自己的 schedule：
   #+begin_src rust
   bevy::core_pipeline::prepass::node::{early_prepass, late_prepass}      // pub fn
   bevy::core_pipeline::tonemapping::tonemapping                          // pub fn
   bevy::core_pipeline::upscaling::upscaling                              // pub fn
   #+end_src
   （=bevy_core_pipeline/src/lib.rs= 里 =pub mod prepass; pub mod tonemapping; pub mod upscaling;=）

** 1.2 其它全局准备（同样与 render graph 无关）
   - =prepare_view_targets= → =Render/RenderSystems::PrepareViews=（提供 =ViewTarget= / =out_texture()= / ping-pong）。
   - =prepare_view_uniforms= → =Render/RenderSystems::PrepareResources=（提供 =ViewUniformOffset= / =ExtractedView=）。
   - =TonemappingPlugin=、=UpscalingPlugin= 的 pipeline 准备也在全局；所以只要把 =tonemapping= / =upscaling= 这两个 *system*
     注册进我们的 schedule，就能拿到完整的 Bevy 后处理（前提：相机带 =Hdr=）。

** 1.3 由此得出的方案
   - **保留并强化 =ShineRenderGraph=**（自定义 camera schedule），**不接入 =Core3d=**。
   - 复用 prepass：把 =early_prepass= 注册进 =ShineRenderGraph=。
   - 复用后处理：M0–M6 先自己写 composite 直接写 =out_texture()=（完全独立、零依赖）；
     M7 再（可选）把 Bevy 的 =tonemapping= + =upscaling= 注册进 =ShineRenderGraph=。
   - 因为不跑 =Core3d=，Bevy 的 PBR 主通道也不会跑 —— 没有「渲染一遍再覆盖」的浪费，正符合「独立管线」的目标。

** 1.4 仍然成立的硬约束（已核实）
   - =ViewPrepassTextures=（=bevy::core_pipeline::prepass=）：=depth=(Depth32Float) / =normal=(Rgb10a2Unorm) /
     =motion_vectors=(Rg16Float) / =deferred=(Rgba32Uint)；提供 =depth_view()/normal_view()/motion_vectors_view()=。
   - 这些纹理 usage 只有 =RENDER_ATTACHMENT | TEXTURE_BINDING=，**没有 =STORAGE_BINDING=**
     → compute 只能只读采样 / =textureLoad=，不能当 storage 写。
   - 它们的 =sample_count= 跟随 =Msaa=，默认 =Msaa::Sample4= → **RT 相机必须 =Msaa::Off=**。
   - normal prepass 写的是 =vec4(in.world_normal * 0.5 + vec3(0.5), 1.0)= → 世界空间法线，解码 =n*2-1=。
   - =early_prepass= 的 =ViewQuery= 需要视图上有 =ExtractedCamera / ExtractedView / ViewDepthTexture /
     ViewPrepassTextures / ViewUniformOffset=（都由全局系统准备，见 1.1）。
   - =ViewTarget::post_process_write()= 会翻转 main texture 并返回 ={source, destination}=（约定「source 写到 destination」）。
   - 引擎内**没有**可复用的 GPU radix sort / prefix sum；唯一可参考的是
     =bevy_pbr/src/cluster/cluster_allocate.wgsl=（workgroup 内 Hillis-Steele scan + 跨块传播）。
   - =bevy_solari= 的 BLAS/TLAS 用 wgpu **硬件光追 API**（=create_blas/create_tlas=），不是 compute 建树，
     对「compute 建 LBVH」没有直接复用价值；但 =realtime/node.rs= 是「compute 只读 =ViewPrepassTextures=」的最佳范例。

** 1.5 通用规律：引擎把每个 pass 拆成「全局 Prepare」+「Core3d 里的执行」
   这是自建 camera schedule 时**最容易漏**的一类问题，M0 阶段已经踩了两次。

   模式是：与相机无关的资源 / 数据准备放在全局 =Render= / =ExtractSchedule=；
   真正推进 GPU 状态的那一步（draw / compute dispatch）放在 =Core3d=。
   所以**复用某个 pass 时，必须去 grep 它在 =Core3d= 里注册了哪些 system，并把它们搬进自己的 schedule。**

   | pass 部分 | 系统 | 引擎注册位置 | 自建 schedule 要做什么 |
   |-----------+------+--------------+------------------------|
   | prepass 绘制 | =early_prepass= / =late_prepass= | =Core3d= | 搬（见 1.1） |
   | GPU mesh preprocessing | =clear_indirect_parameters_metadata= / =unpack_bins= / =early_gpu_preprocess= / =early_prepass_build_indirect_parameters= | =Core3d=（=gpu_preprocess.rs:436=，排 =early_prepass= 之前） | **搬** |
   | GPU occlusion culling 的 late 部分 | =late_gpu_preprocess= / =late_prepass_build_indirect_parameters= | =Core3d= | 启用 =OcclusionCulling= 时才需要 |
   | main pass 的 indirect 参数 | =main_build_indirect_parameters= | =Core3d= | 我们没有 main pass，暂不需要 |
   | tonemapping / upscaling | =tonemapping= / =upscaling= | =Core3d= | M7 可选搬（见 4.9） |

   源码（=bevy_pbr/src/render/gpu_preprocess.rs:436=）：
   #+begin_src rust
   .add_systems(Core3d, (
       (clear_indirect_parameters_metadata, unpack_bins, early_gpu_preprocess,
        early_prepass_build_indirect_parameters.run_if(...))
           .chain()
           .before(early_prepass),        // ← 必须排在 prepass 之前
       ...
   ));
   #+end_src
   这些函数都能通过 =bevy::pbr::*= 访问（=bevy_pbr/src/lib.rs:84= 有 =pub use render::*=，
   =render/mod.rs= 有 =pub use gpu_preprocess::*=），所以不需要 fork 引擎。

   *为什么漏了会「静默不出图」*：GPU preprocessing 是**设备级**的全局选择
   （=MeshRenderPlugin::build= 依 adapter / device 能力决定，无法按相机关闭）。
   设备支持时 phase 处于 =GpuPreprocessingMode::Culling=，此时 phase 的 batch set 是由
   GPU 剔除 + =unpack_bins= 产生的。而 =RenderVisibleEntities<Mesh3d>= 走的是 CPU 可见性路径（有内容），
   所以 =queue_prepass_material_meshes= 会「成功排队」，日志完全看不出问题 ——
   但 =unpack_bins= 没跑 ⇒ phase 里没有实际实例 ⇒ **一个像素都没画出来**，
   表现为全部 prepass 贴图为 0：depth 纯白、normal 均匀灰、motion 均匀灰。

   排查手段：日志只说明「排了队」，看不出「没画」。要么直接对照上面的系统清单，
   要么给相机临时加 =NoIndirectDrawing= 看症状是否改变（phase 会降到 =PreprocessingOnly=，
   走直接绘制；**这不是修法**，只是方向确认）。

* 2. 总体架构
** 2.1 渲染流程
   #+begin_src text
   ExtractSchedule (main -> render)
     extract_rt_scene        : 收集 mesh / 实例 transform / 材质 / RT 开关

   Render (全局，每帧一次；BVH 与相机无关)
     RenderSystems::PrepareResources
       prepare_rt_targets     : 分配 RT storage texture、LBVH 各阶段 buffer、uniform
       prepare_triangle_soup  : 上传三角形 soup（CPU gather）
     RenderSystems::PrepareBindGroups
       prepare_rt_bind_groups
     <RtBuildSystems::Build>  : 自己 encoder + render_queue.submit(...)
       bvh_morton -> bvh_radix_sort(x4) -> bvh_topology -> bvh_refit

   ShineRenderGraph (自定义 camera schedule，每个用它的相机跑一次)
     ShineSystems::Preprocess    : GPU mesh preprocessing（从 Core3d 搬来的 4 个 system，见 1.5）
     ShineSystems::Prepass       : early_prepass  ← Bevy 的 prepass（只注册 system，不接 Core3d）
     ShineSystems::Trace         : compute 光线追踪 → RT storage texture
     ShineSystems::Composite     : 写 out_texture()（M7 后可换成 post_process_write + Bevy tonemapping/upscaling）
   #+end_src

** 2.2 复用清单（明确「复用」与「自研」的边界）
   | 能力                     | 来源            | 我们做什么                                                |
   |--------------------------+-----------------+-----------------------------------------------------------|
   | depth / normal / motion  | Bevy prepass    | 只在 =ShineRenderGraph= 注册 =early_prepass=；其余全自动。 |
   | GPU mesh preprocessing   | Bevy（=Core3d=） | **必须搬 4 个 system 进 =ShineSystems::Preprocess=**（见 1.5）。 |
   | ViewTarget / present      | Bevy 全局        | 用 =ViewTarget::out_texture_color_attachment()=（见 4.9）。 |
   | tonemapping / upscaling  | Bevy（可选）     | M7 后把两个 system 注册进 =ShineRenderGraph=。             |
   | 相机 uniform             | 自研（简洁）     | =inverse_view_proj / camera_position / frame_index ...=   |
   | 材质                     | 自研             | 先从 =StandardMaterial= 抽成 =GpuMaterial=（先只用标量）。 |
   | 三角形 soup              | 自研（CPU 侧）   | 从 =Assets<Mesh> + =GlobalTransform= 展平并上传。          |
   | BVH（LBVH）              | 自研（本次重点） | Morton / Radix Sort / Karras Topology / Refit 全 GPU。     |
   | 遍历 + 着色              | 自研             | 显式栈遍历 + Möller–Trumbore + 直接光/一次间接弹射。        |

** 2.3 BVH 构建放哪里
   - 首选：放在全局 =Render= schedule 的自定义 set（=RtBuildSystems::Build=），
     用 =RenderContext= 或直接 =render_queue.submit([encoder.finish()])= 提交（=bevy_solari::scene::blas= 就是在
     =RenderSystems::PrepareAssets= 里这么干的）。
   - 好处：与相机数量无关，且全局 =Render= 一定早于 =RenderGraph=（camera_driver）运行，
     顺序天然正确，无需跨 schedule 同步。
   - 备选：放进 =ShineRenderGraph=，方便「每帧、每相机」调试与 readback；单相机原型阶段二者等价。

** 3.1 命名约束：shader 必须和 =embedded_asset!= 调用点同目录层级
   =embedded_asset!= / =load_embedded_asset!= 的 asset path 由 =file!()= 推导（找第一个 =src= 前缀，
   再拼上 file 所在目录）。所以：

   - =src/composite.rs= + ="shaders/composite.wgsl"= ⇒ 文件在 =src/shaders/=，asset path
     =bevy_shine/shaders/composite.wgsl=。✓
   - 一旦拆出 =src/bvh/build.rs=，shader 就必须放 =src/bvh/shaders/=，否则 asset path 变成
     =bevy_shine/bvh/shaders/...=，且 =load_embedded_asset!= 必须从同目录的文件里调用。

   **结论：扁平放 =src/shaders/= 最省事；一旦嵌套，shader 目录要跟着嵌套。**

* 4. 关键设计细节
** 4.1 相机与插件接线
   - 例子里的相机（见 =examples/minimal.rs=；**显式用 =ShineRenderGraph=，并且必须 =Msaa::Off=**）：
     #+begin_src rust
     commands.spawn((
         Camera3d::default(),
         CameraRenderGraph::new(ShineRenderGraph),   // 完全独立的管线
         Msaa::Off,                                  // prepass 纹理 sample_count 跟随 Msaa，必须关
         DepthPrepass,
         NormalPrepass,
         MotionVectorPrepass,
         Transform::from_xyz(0.0, 0.0, 1.0).looking_at(Vec3::ZERO, Vec3::Y),
     ));
     #+end_src

   - 插件接线（M0 实际写法）：=ShinePlugin= 只是组合子，实际接线在 =CompositePlugin=。
     #+begin_src rust
     // src/lib.rs
     impl Plugin for ShinePlugin {
         fn build(&self, app: &mut App) {
             app.init_resource::<RtViewMode>()
                 .add_plugins(ExtractResourcePlugin::<RtViewMode>::default())
                 .add_plugins(CompositePlugin);
         }
     }

     // src/composite.rs
     impl Plugin for CompositePlugin {
         fn build(&self, app: &mut App) {
             embedded_asset!(app, "shaders/composite.wgsl");
             let Some(render_app) = app.get_sub_app_mut(RenderApp) else { return };

             ensure_shine_schedule(render_app);      // init_schedule + configure_sets(chain)
             render_app
                 .init_resource::<CompositeUniform>()
                 .init_resource::<SpecializedRenderPipelines<CompositePipeline>>()
                 .add_systems(Render, (write_composite_uniform, prepare_composite_bind_group)
                     .chain().in_set(RenderSystems::PrepareBindGroups))
                 .add_systems(ShineRenderGraph, (
                     // Bevy registers these on Core3d. Without them the prepass
                     // phase has no instances at all, and every view renders
                     // empty (zeros) textures. See 1.5.
                     (
                         clear_indirect_parameters_metadata,
                         unpack_bins,
                         early_gpu_preprocess,
                         early_prepass_build_indirect_parameters,
                     )
                         .chain()
                         .in_set(ShineSystems::Preprocess),
                     early_prepass.in_set(ShineSystems::Prepass),   // ← 复用 Bevy prepass
                     rt_composite .in_set(ShineSystems::Composite),
                 ).chain());
         }

         fn finish(&self, app: &mut App) {
             // 需要 AssetServer，所以必须在所有 build 之后
             app.sub_app_mut(RenderApp).init_resource::<CompositePipeline>();
         }
     }
     #+end_src

   - *接线要点*：
     - =ShineSystems::Preprocess= 里的 4 个 system 是**必须**的，不是可选优化：漏了就会
       「队列排成功、一个像素都不画」（见 1.5）。
     - =ensure_shine_schedule= 用 =init_schedule= 而不是 =add_schedule=。后者是**覆盖式**的
       （源码注释："overwriting any existing schedule with the same label"），多个插件都调会互相清空系统。
     - =SpecializedRenderPipelines= 的 prepare 系统放在 =RenderSystems::PrepareBindGroups=：
       它明确排在 =PrepareResources= 之后，所以 =prepare_prepass_textures= 建好的
       =ViewPrepassTextures= 一定已经存在。
     - =CompositePlugin::finish= 不能合并进 =build=：=load_embedded_asset!= 需要 =AssetServer=，
       而它由 =DefaultPlugins= 里的 =AssetPlugin= 在 =build= 阶段插入；=finish= 保证在所有 =build= 之后运行。
   - =late_prepass= 只在启用 =OcclusionCulling= 时才需要，原型阶段不注册。

** 4.2 三角形 soup（几何输入）
   #+begin_src rust
   #[derive(Clone, Copy, bytemuck::Pod, bytemuck::Zeroable, ShaderType)]
   #[repr(C)]
   pub struct GpuTriangle {
       pub p0: Vec3, pub p1: Vec3, pub p2: Vec3,
       pub n0: Vec3, pub n1: Vec3, pub n2: Vec3,
       pub uv0: Vec2, pub uv1: Vec2, pub uv2: Vec2,
       pub material: u32,
       pub instance: u32,
       pub _pad: [u32; 2],
   }
   #+end_src
   - 收集（M2 先最简）：=ExtractSchedule= 里
     =Extract<Query<(Entity, &Mesh3d, &GlobalTransform, &MeshMaterial3d<StandardMaterial>)>>= → render world，
     配合 =Extract<Res<Assets<Mesh>>>= 展平三角形并做世界变换。
   - =src/mesh.rs= 的 =GpuTriangles::from_mesh= 在 M0 重构时被删掉了；M2 需要时从 git 历史
     =3d3058d= 取回，或按下面的字段重新写一份（要求 position / normal / uv 齐全）。
   - 优点：与 Bevy mesh allocator 解耦，易调试。缺点：CPU gather。M9 改成 GPU 反索引化。
   - 演进：mesh 集合变化 → 重建整棵树；只变 transform → 走 refit only（M8）。

** 4.3 Morton Code（30-bit）
   - 先 reduce 求全场景 AABB。三角形取重心 =c=，归一化 =t=(c-min)/(max-min)=，clamp [0,1)。
   - 量化 =q_i = min((u32)(t_i*1024.0), 1023u)=（每轴 10 bit）。
   #+begin_src wgsl
   fn expand_bits(v: u32) -> u32 {          // 10-bit -> 30-bit interleave
       var x = v & 0x3FFu;
       x = (x | (x << 16u)) & 0x030000FFu;
       x = (x | (x <<  8u)) & 0x0300F00Fu;
       x = (x | (x <<  4u)) & 0x030C30C3u;
       x = (x | (x <<  2u)) & 0x09249249u;
       return x;
   }
   fn morton3(qx: u32, qy: u32, qz: u32) -> u32 {
       return expand_bits(qx) | (expand_bits(qy) << 1u) | (expand_bits(qz) << 2u);
   }
   #+end_src
   - 输出 =mortons: array<u32>= 与 =triangle_ids: array<u32>=。CPU 参考实现必须逐位一致。

** 4.4 GPU Radix Sort（LSD，4 pass × 8 bit）
   - 4 个 pass，每 pass 处理 8 bit；每 pass 三个 kernel：
     1. =radix_histogram.wgsl=：workgroup（256 线程）处理 =256*ITEMS= 个元素（=ITEMS≈16=），
        共享内存统计 256 桶，写 =block_histograms[block*256+bin]=。
     2. =radix_scan.wgsl=：按 bin 做 exclusive scan：先 workgroup 内 scan（256 bin = 256 线程），
        再跨 workgroup 累加（原型阶段 block 少，可单 workgroup 串行；或做 chained scan）。
        输出 =block_offsets[block*256+bin]=。
     3. =radix_scatter.wgsl=：重读 chunk，共享内存重算 local rank，写 =out_keys/out_ids=。
   - 双缓冲 ping-pong（=keys_a/keys_b=、=ids_a/ids_b=），4 pass 后固定回 A。
   - 尾块要处理（=min(n, chunk_end)=）。
   - 规模假设：≤ 2^20 三角形。可先写一个「小规模 bitonic sort」把通路跑通，再替换成 radix。

** 4.5 Karras LBVH Topology（internal node i = LCA(leaf i, leaf i+1)）
   - 约定：叶子下标 = =N-1+k=；内部节点下标 = =0..N-1=；总节点 = =2N-1=。
   - =delta(i,j)= = Morton key i、j 的最长公共前缀；越界返回 -1。
   - 每个内部节点 i：=d= 由 =delta(i,i+1)= 与 =delta(i,i-1)= 比较得出；倍增 + 二分求 =j=；再二分求 split；
     得 =first=min(i,j)=、=last=max(i,j)=、=split=。
   - 子节点编号（本方案的核心不变式）：
     #+begin_src text
     左子 = (split > first)     ? 内部节点 first   : 叶子 N-1+first
     右子 = (last  > split+1)   ? 内部节点 split+1 : 叶子 N-1+(split+1)
     因为节点 i 定义为 LCA(leaf i, leaf i+1)，所以区间 [a,b] 的内部节点号就是 a。
     #+end_src
   - =atomicMin(parent[child], i)= 写父子关系；=parent= 初始 =0xFFFFFFFF=。
     - 根 = 唯一 =parent == 0xFFFFFFFF= 的内部节点（**不是**恒为 0，必须显式求）。
   - 输出 =node_links: array<vec4<u32>>=，每节点 =[child_a, child_b, parent, flags]=；
     =flags & 1= 表示叶子，此时 =child_a= = 三角形下标。

** 4.6 Atomic Bottom-Up AABB Refit
   - 布局（避开 WGSL 对齐坑）：
     #+begin_src text
     node_bounds : array<vec4<f32>>  // 每节点 2 个: [min.xyz, pad] / [max.xyz, pad]
     node_links  : array<vec4<u32>>  // 每节点 1 个: [child_a, child_b, parent, flags]
     #+end_src
   - Refit 时把 =node_bounds= 以 =array<atomic<u32>>= 重新绑定（同一 buffer、另一种视图；
     =vec4<f32>= 16 字节对齐，平铺 u32 也是 4 字/16 字节，布局安全）。
   - R1：每个叶子算三角形 AABB，直接写 =node_bounds[N-1+k]=（一对一，无需原子）。
   - R2：每个叶子从 =parent= 走到根，对每个祖先 =atomicMin/atomicMax=。
     - 原子 min/max 满足交换律/结合律 → 顺序无关、天然正确。
     - **不要**用「按下标倒序、每节点 atomic 到父节点」的单 pass 写法（有竞态）。
   - float 原子比较必须用单调映射（WGSL 无 float 原子）：
     #+begin_src wgsl
     fn f32_to_ordered(x: f32) -> u32 {
         let b = bitcast<u32>(x);
         return select(b | 0x80000000u, ~b, (b & 0x80000000u) != 0u);
     }
     fn ordered_to_f32(k: u32) -> f32 {
         let b = select(k & 0x7FFFFFFFu, ~k, (k & 0x80000000u) == 0u);
         return bitcast<f32>(b);
     }
     #+end_src
   - 增量（M8）：只更新变化叶子 → 只跑 R1+R2（拓扑不变）= refit only。

** 4.7 光线遍历与着色（=trace.wgsl=）
   - 相机 uniform（自研，简洁）：=inverse_view_proj / view_proj / camera_position / frame_index / light_dir / light_radiance=。
   - 主光线：像素 → uv → ndc → =inverse_view_proj= 反投影（近/远平面两点做 ray）。
   - 天空判定：先读 prepass depth，=depth==1.0=（反向 Z 时 ==0）视为无几何（可直接输出背景/环境光）。
   - 遍历（显式定长栈，比 hikari 的无栈跳转更好调试）：
     #+begin_src wgsl
     var stack: array<u32, 64>;
     var sp = 0u; stack[0] = root; sp = 1u;
     loop {
         if (sp == 0u) { break; }
         sp -= 1u;
         let node = stack[sp];
         if (intersect_aabb(ray, node_bounds[node]) >= hit_dist) { continue; }
         let link = node_links[node];
         if ((link.w & 1u) != 0u) {           // 叶子
             test_triangle(link.x);           // Möller–Trumbore，更新最近命中
         } else {
             stack[sp] = link.x; sp += 1u;     // 可选：按距离排序压栈以提高 early-out
             stack[sp] = link.y; sp += 1u;
         }
     }
     #+end_src
   - 命中后：重心插值 UV/法线，查材质，着色。
   - 着色（参照 hikari 但简化）：方向光 + 太阳圆盘（=cos(SOLAR_ANGLE)=）+ 阴影光线；
     自发光面 =emissive*255=；余弦半球采样 1 次间接弹射（共 2 次弹射，保留开关）；
     BRDF 先 Lambert + Fresnel，逐步替换为 Filament 风格。
   - 输出 RT storage texture（=Rgba16Float=，线性 HDR，**不乘 exposure**）。

** 4.8 复用 prepass 的绑定

** 4.9 输出与后处理
   - *必须走 =out_texture_color_attachment()=，不能手搓 =RenderPassColorAttachment=。*

     =OutputColorAttachment= 用内部 =is_first_call= 原子标记「被写过」：
     #+begin_src rust
     pub fn get_attachment(&self, clear_color: Option<LinearRgba>) -> RenderPassColorAttachment<'_> {
         let first_call = self.is_first_call.fetch_and(false, Ordering::SeqCst);   // ← 一次性令牌
         ...
     }
     /// Returns `true` if this attachment has been written to by a render pass.
     pub fn needs_present(&self) -> bool { !self.is_first_call.load(Ordering::SeqCst) }
     #+end_src
     而 =render_system= 的 present 逻辑是 =if view_needs_present || window.needs_initial_present=，
     其中 =needs_initial_present= 只兜第一帧。手搓 attachment 会绕开 =get_attachment()= ⇒
     标志位永远是 true ⇒ **窗口只在第一帧 present 一次，之后永远冻结** ⇒
     表现为「日志全绿（pipeline/bind group/draw 全部成功）+ 屏幕全黑」。

     #+begin_src rust
     let Some(color_attachment) =
         view_target.out_texture_color_attachment(Some(LinearRgba::BLACK))
     else { return; };
     #+end_src

   - 像素格式用 =view_target.out_texture_view_format()= 决定（不要硬编码 =Bgra8UnormSrgb=）。
   - *M0–M6（完全独立）*：composite 直接写 =out_texture()=，shader 里做简易 tonemap。零外部依赖。
   - *M7（可选复用）*：把 =tonemapping= + =upscaling= 注册进 =ShineRenderGraph=：
     composite 改为写 =post_process_write().destination=，然后 =tonemapping= → =upscaling= 链路。
     需要相机加 =Hdr=；这两个 system 与它们的 pipeline 都是全局准备好的，可直接复用。
   - 注意 =upscaling= 才是最终 blit 到 =out_texture= 的那一步。
   - *通用规律*：同一资源同时提供「裸 view」和「带簿记的 attachment」两个入口时，一定用后者 ——
     =out_texture()= / =out_texture_color_attachment()=、=main_texture_view()= / =post_process_write()=。
