* Commit 拆分与说明参考
  依据 Linux 官方 [[https://docs.kernel.org/process/submitting-patches.html][Submitting patches]]，重点参考
  [[https://docs.kernel.org/process/submitting-patches.html#separate-your-changes][Separate your changes]]、[[https://docs.kernel.org/process/submitting-patches.html#describe-your-changes][Describe your changes]] 和
  [[https://docs.kernel.org/process/submitting-patches.html#style-check-your-changes][Style-check your changes]]。核对日期：2026-11-12。
  下文提炼可用于本项目的原则，不是完整的 Linux 内核投稿流程。

** Linux 官方原则
   - *一个 patch 只包含一个逻辑变化* 。在本项目中，按一个 patch 对应一个 commit 理解。
     Bug 修复与性能优化应分开；API 更新与使用该 API 的新功能可以分开。
   - *按逻辑拆分，不按文件拆分* 。一个变化涉及多个文件时，应放在同一提交中；
     同一文件中的不相关变化，也应拆成不同提交。
   - *每个提交都应容易理解、可由审阅者验证，并有自身成立的理由* 。
     小型化的目的在于降低审阅难度，而不是机械地把代码切碎。
   - *允许提交之间存在依赖* 。不要求每个提交都能脱离前面的提交独立应用；
     需要依赖时，在说明中写明“本提交依赖第 X 个提交”及原因。
   - *系列中的每个中间状态都必须能够正常构建和运行* 。
     不能先提交破坏构建或已有运行路径的半成品，再由后续提交修复；
     =git bisect= 可能停在系列中的任意位置。
   - *代码搬移与行为修改分开* 。搬移代码的提交不要同时修改被搬移代码，
     以便审阅真实变化并追踪历史；不相关的格式清理也不要混入功能提交。
   - *提交说明应自包含* ：说明问题、影响、为什么值得解决，以及具体如何解决。
     不应要求审阅者先阅读旧版补丁或外部讨论才能理解；引用链接时也要概括关键理由。
   - *性能收益要有数据，代价也要说明* 。不能只写“更快”或“更省内存”；
     应给出支撑数字，并交代 CPU、内存、可读性或不同负载之间的权衡。
   - 提交前检查代码风格；工具检查不能代替人工判断。
   - *上述指南没有规定每个提交固定多少行* 。大小取决于逻辑完整性和可审阅性。
     指南中“每次约发 15 个 patch”的建议是较大系列的分批投稿建议，不是代码行数限制。

** 在本项目中的落实方式
   以下为项目协作约定，不冒充 Linux 官方原文：
   - 每批先说明目标、改动文件、输入输出、预期行为和边界；使用可审阅的定向编辑。
   - 将验证同一逻辑变化所需的测试与实现放在一起；无关测试或重构另行拆分。
   - 准备工作可以单独提交，例如先建立并测试 CPU BVH，再接入 GPU 上传。
     这种提交不必已经提供最终可见效果，但应有明确用途、可检查结果且不破坏已有路径。
   - 每个提交记录实际验证范围：编译、CPU 测试、GPU 运行、视觉检查、性能测量分别说明。
     没有执行、被环境阻塞、执行失败都应如实记录，不能把编译成功写成功能验证通过。
   - 拆分数量由逻辑边界决定；既不为了“够小”拆出无法验证的碎片，
     也不把数据准备、上传、查询、接触响应和动态更新全部混成一个大提交。
   - 用户审阅和验证后再决定下一批；agent 不自动执行 Git commit。

** 提交说明检查清单
   - 标题：受影响模块 + 具体变化，而不是仅写文件名或“更新代码”。
   - 问题与目的：本提交解决什么问题，为什么现在需要它？
   - 实现与边界：采用什么方法，哪些行为改变，哪些内容明确不在本次范围？
   - 依赖：依赖哪些前置提交，应用到此前序列后能否构建并保持已有运行路径？
   - 验证：执行了什么命令或场景，实际结果是什么，哪些项目仍未验证？
   - 若声称性能改善：测量条件、前后数据和代价是否齐全？

** Step 3 implementation and review boundary
   Goal: prepare GPU collision geometry only; no query dispatch or contact response.
   - Files: =bvh.rs= adds Clone; =collider.rs= owns CPU assets and extracted references;
     =collider_gpu.rs= prepares buffers; =mod.rs= registers the plugins. Existing solver bindings are unchanged.
   - Each successful preparation creates a new =ColliderGeometry= asset. =PreparedCollider= holds its strong Handle.
     Default render-asset extraction clones CPU data on asset addition/modification, not every frame.
     There is no Arc snapshot, custom upload queue, version counter or unavailable-state enum.
   - =GpuCollider= contains positions, indices, nodes and triangle_refs buffers, plus valid counts.
     Buffer usage is STORAGE only. CPU preparation validates geometry; GPU preparation does not duplicate it.
     Device validation/OOM/loss follows Bevy's renderer error handling, not a local warn-and-skip guarantee.
   - =RenderAssetPlugin= manages preparation, storage and unused-asset cleanup.
     Active queries must start from collider entities and resolve their Handles, not iterate all stored GPU assets.
     Removing a reference stops participation; physical resource reclamation can happen later.
     Failed CPU replacement removes the old reference. No automatic CPU preparation retry is introduced.
   - CollisionGroup is extracted independently on change; absence means 0. Group changes do not upload geometry.
   - Independently moving collider instances need separate world-space geometry assets, even with the same source Mesh.
     Multiple cloths can query one collider without uploading separate copies of that collider.
   - leaf_nodes/internal_nodes upload remains step 8; refit_layers remains CPU scheduling metadata.
     History remains step 7; runtime query bindings and dispatch will be connected with contact integration.
   - CPU test review: asset lookup, stable identity on group changes, new identity on Mesh replacement,
     failed replacement, input removal/despawn, separate instance assets and strong-handle lifetime.
     GPU review still requires first upload, unchanged frames, replacement/removal and group-only changes.
   - Host validation: =cargo test -j 2 -p bevy_cloth xpbd::collider::tests -- --nocapture=;
     then run a GPU fixture with MeshCollider inputs and inspect CPU/GPU preparation logs.
     =xpbd-solver= currently has no collider fixture, so running it alone does not validate collider upload.

** Step 4 current review batch: GPU query functions only
   - =bvh_query.wesl=: segment fallback, seven-region closest point, AABB pruning,
     near-child-first stack traversal and final winding face normal.
     The geometry routine follows [[https://github.com/NVIDIA/warp/blob/82dab030eeb6088e180922bc60aa167a2038e457/warp/native/intersect.h#L44-L109][NVIDIA Warp's CUDA implementation]]. Changes: relative-vector inputs, three weights and zero-area segment fallback.
   - Removed =collider_query.rs=: probe components, request collection/versioning, result resources,
     channels, readback buffers, diagnostic pipeline and dispatch. No replacement diagnostic framework or example.
     Removed their plugin registration and the probe compute entry; four read-only geometry bindings remain.
   - =closest_hit(p)= returns the original triangle ID, closest point/distance squared, barycentrics,
     winding normal and completion status directly within the shader. No CPU result ABI or exported visit statistics.
     The local traversal counter only bounds traversal; stack/numeric failure status prevents using a partial answer.
   - The shader is embedded but has no compute entry or active caller yet. Contact integration must provide
     the runtime binding layout and particle entry point. No existing simulation behavior changes in this batch.
   - Stack capacity remains 64; overflow returns failure. Direct f32 arithmetic retains scale/skinny-triangle risks.
     Query distance is unsigned; a winding face normal is not a global inside/outside classifier.
   - Cleaned shader passed actual-source Naga parsing/module validation: closest_hit retained,
     four read-only bindings, no compute entry. Rust formatting and git diff --check passed.
     Workspace offline Cargo remains blocked before compilation by missing avian3d for bevy_waltz.
     No numerical execution, GPU run or performance result is claimed.

** 后续接触与动态更新的既有约定
   - 外部网格单向作用于布料；碰撞组按值精确相等，缺失为 0。
   - 保留历史局部接触语义：默认按绕序的外向实体壳，可选双面；厚度和摩擦取布料参数。
     跳过零逆质量粒子及退化面；每个网格取一个最近三角形，不声称全局严格内外判断。
   - 第 5 步接入时说明接触与内部约束的具体先后顺序及残差，不静默改变历史语义。
     历史接触在内部求解前执行，内部约束可能重新引入穿透；是否增加最终修正需讨论验证。
   - BVH 使用世界空间。动态更新先从顶点生成当前世界坐标，再 refit；旋转时不能直接变换旧 min/max。
   - 当前/历史几何共享 tick、epoch 和 dt；历史推进与渲染帧数分开。
     摩擦使用同一三角形、同一重心坐标的当前/历史表面位移，并按子步分配。
   - refit 保持拓扑和三角归属，先并行叶节点，再最深层到根逐层更新内部节点。
     不在每件布料或每轮内部迭代中重复更新同一时刻的人体几何。
