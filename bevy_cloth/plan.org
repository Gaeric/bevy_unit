* Commit 拆分与说明参考
  依据 Linux 官方 [[https://docs.kernel.org/process/submitting-patches.html][Submitting patches]]，重点参考
  [[https://docs.kernel.org/process/submitting-patches.html#separate-your-changes][Separate your changes]]、[[https://docs.kernel.org/process/submitting-patches.html#describe-your-changes][Describe your changes]] 和
  [[https://docs.kernel.org/process/submitting-patches.html#style-check-your-changes][Style-check your changes]]。核对日期：2026-11-12。
  下文提炼可用于本项目的原则，不是完整的 Linux 内核投稿流程。

** Linux 官方原则
   - *一个 patch 只包含一个逻辑变化* 。在本项目中，按一个 patch 对应一个 commit 理解。
     Bug 修复与性能优化应分开；API 更新与使用该 API 的新功能可以分开。
   - *按逻辑拆分，不按文件拆分* 。一个变化涉及多个文件时，应放在同一提交中；
     同一文件中的不相关变化，也应拆成不同提交。
   - *每个提交都应容易理解、可由审阅者验证，并有自身成立的理由* 。
     小型化的目的在于降低审阅难度，而不是机械地把代码切碎。
   - *允许提交之间存在依赖* 。不要求每个提交都能脱离前面的提交独立应用；
     需要依赖时，在说明中写明“本提交依赖第 X 个提交”及原因。
   - *系列中的每个中间状态都必须能够正常构建和运行* 。
     不能先提交破坏构建或已有运行路径的半成品，再由后续提交修复；
     =git bisect= 可能停在系列中的任意位置。
   - *代码搬移与行为修改分开* 。搬移代码的提交不要同时修改被搬移代码，
     以便审阅真实变化并追踪历史；不相关的格式清理也不要混入功能提交。
   - *提交说明应自包含* ：说明问题、影响、为什么值得解决，以及具体如何解决。
     不应要求审阅者先阅读旧版补丁或外部讨论才能理解；引用链接时也要概括关键理由。
   - *性能收益要有数据，代价也要说明* 。不能只写“更快”或“更省内存”；
     应给出支撑数字，并交代 CPU、内存、可读性或不同负载之间的权衡。
   - 提交前检查代码风格；工具检查不能代替人工判断。
   - *上述指南没有规定每个提交固定多少行* 。大小取决于逻辑完整性和可审阅性。
     指南中“每次约发 15 个 patch”的建议是较大系列的分批投稿建议，不是代码行数限制。

** 在本项目中的落实方式
   以下为项目协作约定，不冒充 Linux 官方原文：
   - 每批先说明目标、改动文件、输入输出、预期行为和边界；使用可审阅的定向编辑。
   - 将验证同一逻辑变化所需的测试与实现放在一起；无关测试或重构另行拆分。
   - 准备工作可以单独提交，例如先建立并测试 CPU BVH，再接入 GPU 上传。
     这种提交不必已经提供最终可见效果，但应有明确用途、可检查结果且不破坏已有路径。
   - 每个提交记录实际验证范围：编译、CPU 测试、GPU 运行、视觉检查、性能测量分别说明。
     没有执行、被环境阻塞、执行失败都应如实记录，不能把编译成功写成功能验证通过。
   - 拆分数量由逻辑边界决定；既不为了“够小”拆出无法验证的碎片，
     也不把数据准备、上传、查询、接触响应和动态更新全部混成一个大提交。
   - 用户审阅和验证后再决定下一批；agent 不自动执行 Git commit。

** 提交说明检查清单
   - 标题：受影响模块 + 具体变化，而不是仅写文件名或“更新代码”。
   - 问题与目的：本提交解决什么问题，为什么现在需要它？
   - 实现与边界：采用什么方法，哪些行为改变，哪些内容明确不在本次范围？
   - 依赖：依赖哪些前置提交，应用到此前序列后能否构建并保持已有运行路径？
   - 验证：执行了什么命令或场景，实际结果是什么，哪些项目仍未验证？
   - 若声称性能改善：测量条件、前后数据和代价是否齐全？

** 第 3 步待确认的实现方案
   目标只到“GPU 拥有可查询的碰撞几何”，不包含查询 dispatch 或接触响应。
   - 文件范围：修改 =collider.rs=、=mod.rs=，新增 =collider_gpu.rs=；不改现有拉伸 solver binding。
   - CPU 几何：拟将 positions、indices、TriangleBvh 放进不可变 =ColliderGeometry=，
     由 =PreparedCollider= 持有 =Arc<ColliderGeometry>=；每次准备成功创建新快照。
     Render World 提取只克隆 Arc，不深复制整份网格；只在准备结果变化时提取。
   - GPU：每个碰撞体拥有一套 =GpuCollider=，包含 positions、indices、nodes、triangle_refs 四个 Buffer
     以及有效数量和来源快照；多件布料共享同一碰撞体，不各自上传人体副本。
   - 本阶段拟用快照身份识别几何版本，不额外维护递增计数器；这是待确认方案。
     未来异步任务需要跨任务版本标识时再讨论，不提前增加重建框架。
   - 上传前检查四个 Buffer 的非空和设备容量限制，再整体创建/替换组件；不混用新旧数组。
     当前只需 STORAGE 用途，后续有实际复制需求时再增加 COPY_SRC/COPY_DST。
   - Main World 移除 PreparedCollider 时，同步清理 Render World 的准备结果和 GpuCollider。
     新版 CPU 准备失败或 GPU 容量检查失败时，旧 GPU 碰撞体不得继续生效；不自动重试。
   - CollisionGroup 单独按变化提取，缺失视为 0；改组号不重新上传几何。
   - leaf_nodes/internal_nodes 到第 8 步再上传；refit_layers 留 CPU 调度。
     历史顶点到第 7 步引入；查询 binding、pipeline、探针及回读到第 4 步实现。
   - 测试重点：首次上传一次、不变不上传、同实体替换、失败清旧结果、移除/销毁、改组不上传。
     生命周期测试与实际 GPU Buffer 上传验证分别记录。

** 后续接触与动态更新的既有约定
   - 外部网格单向作用于布料；碰撞组按值精确相等，缺失为 0。
   - 保留历史局部接触语义：默认按绕序的外向实体壳，可选双面；厚度和摩擦取布料参数。
     跳过零逆质量粒子及退化面；每个网格取一个最近三角形，不声称全局严格内外判断。
   - 第 5 步接入时说明接触与内部约束的具体先后顺序及残差，不静默改变历史语义。
     历史接触在内部求解前执行，内部约束可能重新引入穿透；是否增加最终修正需讨论验证。
   - BVH 使用世界空间。动态更新先从顶点生成当前世界坐标，再 refit；旋转时不能直接变换旧 min/max。
   - 当前/历史几何共享 tick、epoch 和 dt；历史推进与渲染帧数分开。
     摩擦使用同一三角形、同一重心坐标的当前/历史表面位移，并按子步分配。
   - refit 保持拓扑和三角归属，先并行叶节点，再最深层到根逐层更新内部节点。
     不在每件布料或每轮内部迭代中重复更新同一时刻的人体几何。

     上衣最大顶点度数为 29，后 19 个颜色组各仅 2 条约束，需实测小 dispatch 开销。
   - 按原索引裙子有 3 个连通分量，上衣有 116 个；精确重合顶点连接后各为 1 个。
     当前新 XPBD 不连接这些渲染拆分，真实衣物验证前需单独讨论接缝/模拟映射，不能当完整衣物拓扑。
   - 本资产没有 skin/animation；人体蒙皮性能不属于本次已验证结果。
   - 后续性能测量区分 CPU 命令记录、拉伸、BVH 查询、refit、Mesh 输出；查询频率必须随测量说明。
     CPU 访问量诊断不是 GPU 计时，refit 正确也不保证变形后遍历质量一直良好。
